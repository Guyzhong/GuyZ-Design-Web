权限治理 一致性 IDP 后台

权限与状态一致性治理：
让同一动作在不同模块不再"性格分裂"

一句话结论：统一了 5 大模块的权限判断逻辑与状态流转规范，消灭了 23 处行为不一致问题（同一按钮在不同模块表现不同），用户投诉减少 78%，新模块接入成本降低 60%。
背景与约束

"删除"按钮在 A 模块弹确认框，在 B 模块直接删

该 IDP 在两年间由 3 个团队交替维护，5 大核心模块（配置管理、内容管理、环境管理、流水线、权限中心）分别在不同时期开发。结果是：同一个"删除"操作，在配置管理里会弹二次确认，在内容管理里直接执行；同一个"只读"状态，在 A 模块灰掉按钮，在 B 模块隐藏按钮，在 C 模块显示按钮但点击报错。

  • 业务目标：统一交互行为、降低用户困惑和投诉
  • 核心角色：所有使用者（200+），特别是跨模块操作频繁的 SRE
  • 历史包袱：5 个模块、3 个前端团队、没有统一的交互规范文档
  • 研发资源：规范制定 + 2 名前端渐进式改造，窗口 4 周
问题证据

23 处"性格分裂"：问题图谱

通过全模块走查（5 个模块 × 8 个高频操作 × 3 种角色），建立了一张"行为一致性审计表"：

  • 权限态不一致（9 处）：无权限时的表现形态不统一——灰掉、隐藏、显示但报错，三种方式混用
  • 危险操作处理不一致（6 处）：删除/停用等高风险操作，有的有二次确认，有的没有，有的确认文案是通用模板
  • 状态流转不一致（5 处）：草稿→发布的流转在不同模块有不同步骤数和校验规则
  • 错误反馈不一致（3 处）：操作失败时 toast / 弹窗 / 页内提示混用，定位和持续时间各不同
关键取舍

先定规范，再分批改造，不追求一步到位

  • 先规范后实现：第 1–2 周出规范文档 + 组件模式，第 3–4 周在最高频的 2 个模块落地，其余模块按迭代节奏渐进替换
  • 不改底层权限模型：后端权限判断逻辑不动，只统一前端的"权限态"表现形态
  • 定一条原则："无权限 = 灰掉 + tooltip 说明原因"，不隐藏、不让点击后报错——让用户"看得到自己没有什么"，而不是"不知道还有什么"
  • 暂不做：细粒度权限配置界面改版（排入后续迭代）
方案展示

四层规范：从原则到组件

Before
  • 无权限：灰掉/隐藏/可点但报错，混用
  • 危险操作：有/没有二次确认，随缘
  • 状态流转：各模块自定义，步骤数不同
  • 错误提示：toast/弹窗/页内提示混用
  • 新模块接入：从零写交互逻辑
After
  • 统一：灰掉 + tooltip 说明缺什么权限
  • 统一：所有危险操作必弹确认 + 影响说明
  • 统一：状态机模型 + 流转规则文档
  • 统一：toast 用于成功/信息，弹窗用于需确认
  • 新模块接入：复用规范组件，成本降 60%

规范体系分四层：①原则层（可预测、可解释、可回退）→ ②模式层（权限态、危险操作、状态流转、错误反馈 4 个模式）→ ③组件层（PermissionGuard / DangerConfirm / StatusBadge 等封装组件）→ ④验收层（checklist + 走查脚本）。

落地协作

跨团队对齐：让三个前端团队用同一套规则

  • 规范评审会：邀请 3 个前端团队 + 产品负责人，逐条过规范条目，现场决议边界 case
  • 组件化交付：封装 PermissionGuard / DangerConfirm / StatusFlow 三个核心组件，附使用文档和 Storybook 示例
  • 渐进式迁移计划：配置管理和内容管理在当期改完，其余模块各自排期，确保不阻塞各团队节奏
  • 验收走查：设计侧产出 23 条 checklist（对应 23 处不一致），改一条勾一条
复盘与下一步

"一致性"是个持续工程

  • 已验证：用户投诉减少 78%（月均 18 条→4 条），新模块接入交互开发成本降低 60%，SRE 跨模块操作效率明显提升（不再需要"适应"不同模块的脾气）
  • 待深入：权限中心自身的管理界面改版（当前管理端也有一致性问题）、细粒度权限的前端可视化、自动化一致性检测（CI 级别的走查）
