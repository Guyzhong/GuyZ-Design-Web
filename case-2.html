内容管理提效：
从"层层点开"到"一屏完成发布与校验"

一句话结论：重构了内容发布的核心链路，把 3 页分散的操作（编辑→预览→发布）合并为 1 屏联动完成，发布耗时减少 55%，校验遗漏问题归零。
背景与约束

运营每天发 20+ 条内容，每条要跳 3 个页面

该平台的内容管理模块负责面向研发的公告、变更通知、文档片段等内容的发布。运营同学每天要处理 20–30 条内容，但发布一条内容需要：进编辑页填写 → 跳到预览页确认 → 回到列表页点发布。三个页面来回跳，每条内容平均耗时 4.5 分钟。

  • 业务目标：提升内容发布效率，减少校验遗漏
  • 核心角色：内容运营（日均 20+ 次操作）、审核人（抽查确认）
  • 历史包袱：编辑器、预览、发布分属不同迭代期间开发，未做链路整合
  • 研发资源：1 名前端 + 1 名后端，改版窗口 2 周
问题证据

录屏 + 工单：三个断裂点

通过录屏观察 3 位运营同学的操作流程，结合近 2 个月的内部工单：

  • 编辑 → 预览断裂：编辑完成后必须手动点"保存草稿"，然后跳到预览页——如果忘记保存，预览看到的是旧版本，已发生 7 次事故
  • 预览 → 发布断裂：预览页没有"直接发布"按钮，需要返回列表页找到该条目再点发布，路径冗长
  • 校验遗漏：必填字段校验只在提交时触发，运营经常填了半小时才发现标题/封面图漏了
关键取舍

合并页面 vs. 优化跳转？我选合并

当时有两个方案可选：

  • 方案 A（选中）：编辑/预览/发布合并为一屏，左编辑右预览，底部发布栏常驻——代价是前端需要重构页面布局
  • 方案 B（放弃）：保留三页结构，优化页面间跳转速度和自动保存——代价低但用户体感改善有限
  • 决策依据：运营同学的核心痛点是"来回跳"而非"跳得慢"，合并页面从根本上消灭了这个问题
  • 暂不做：内容模板系统（频次不够高）、批量发布（需要后端 API 改造，排入下期）
方案展示

一屏三区：编辑 / 预览 / 发布一气呵成

Before
  • 编辑、预览、发布分散在 3 个页面
  • 手动保存草稿，容易遗忘
  • 校验仅在最终提交时触发
  • 无实时预览，编辑和预览脱节
  • 单条发布耗时 4.5 分钟
After
  • 左编辑 + 右预览 + 底部发布栏，一屏完成
  • 自动保存，300ms 防抖，告别手动保存
  • 实时校验 + 字段级错误提示
  • 编辑即预览，所见即所得
  • 单条发布耗时 2 分钟，降低 55%

关键交互细节：底部发布栏设计为"粘性固定"，始终显示当前内容状态（草稿/待审核/已发布）和校验进度（3/5 项已完成），让运营同学在编辑过程中始终知道"我离发布还差几步"。

落地协作

前后端协作：接口先行，组件跟进

  • 接口对齐：与后端确认自动保存 API（防抖策略、冲突处理），实时校验无需新增接口，前端本地完成
  • 组件拆分：编辑区、预览区、发布栏拆为独立组件，前端可并行开发、独立测试
  • 验收 checklist：覆盖 8 个关键状态（空状态、自动保存触发、校验报错、网络断开恢复等），逐一走查
复盘与下一步

效率翻倍，但还有空间

  • 已验证：发布耗时从 4.5 分钟降至 2 分钟（-55%），校验遗漏问题从月均 7 次降至 0 次，运营满意度评分从 3.2→4.6（5 分制）
  • 待深入：内容模板系统（减少重复填写）、批量发布能力（后端 API 改造中）、内容版本对比（目前只有最新版本快照）
